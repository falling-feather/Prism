# 映物性能优化：测量与建议

日期：2026-09-26。状态：用户已确认并完成第一阶段“快速导出＋轻量编辑”，应用版本0.3.1，工程协议仍为 SVGFilm 0.3。下方原型数据保留用于比较，正式实现的结果见下一节。

## 第一阶段交付结果

### 实现

- 自动／快速／兼容三种MP4导出方式；自动模式少于90帧使用兼容方式，避免短任务初始化开销；暂不支持的滤镜、遮罩和图案等效果自动回退并保留原因。
- 快速编码最多4个待编码请求，每批最多一秒／60帧，单批压缩数据上限16 MiB；每批排空后传给Python写入压缩视频，再由FFmpeg封装和统一混音。不积累整片图片或整片编码数据。
- 取消覆盖载入、编码能力检测、图片解码、编码等待和FFmpeg阶段；成功、取消及失败均释放编码器、临时码流与音频文件。
- 撤销快照共享冻结的来源对象和音频字符串，复制较小的编辑状态；已验证素材与UTF-8字节数可复用，编辑元数据仍完整校验，保留120 MiB预算与无效编辑回滚。
- 复用原SVG节点、文字引用和字幕节点；普通编辑／撤销不重建所有来源，面板及时间条按内容签名更新；播放头pointermove按requestAnimationFrame合并并在松手时提交最后位置。
- API未提供exportMode时继续默认兼容；应用版本通过health与工程schemaVersions分别报告，不改变旧工程结构或作者接口。

### 正式链路对比

同一台电脑、同一细胞工程高尔基体镜头、相同帧率，串行测试。墙钟时间包含提交、浏览器启动、视频生成、音频混合和状态轮询；不同编码器的画质控制参数不完全相同。数据为本机单次测量，不作为所有设备的性能承诺。

| 样片 | 兼容模式 | 快速模式 | 耗时减少 |
| --- | ---: | ---: | ---: |
| 720p，12秒，360帧 | 21.392秒 | 15.797秒 | 26.2% |
| 1080p，8秒，240帧 | 20.859秒 | 14.374秒 | 31.1% |

在这两组任务中，单批编码数据峰值分别约0.52 MiB和0.86 MiB，待编码队列峰值均为4。

进程树工作集合计峰值（包含服务及导出子进程，不含独立显存；共享页可能重复计数）：720p兼容约1449 MiB、快速约1522 MiB；1080p兼容约2077 MiB、快速约1491 MiB。加速不等于所有场景都降低内存；本版保证队列有界，保留兼容选择。

同一工程重复25次的编辑基础操作：

| 操作 | 原完整处理：中位数／P95 | 新处理：中位数／P95 |
| --- | ---: | ---: |
| 编辑快照 | 8.7／29.3ms | 1.6／3.0ms |
| 工程校验 | 87.3／106.1ms | 1.8／2.9ms |

这些是基础操作的耗时，不等同于完整UI交互耗时。实际交互回归确认80次连续播放头移动合并为1次画面更新，撤销保持来源DOM身份，字幕在内容不变时保持节点身份。

### 质量与验证

快速／兼容2秒工程均解码为60帧，逐像素平均绝对差约0.61/255；透明画布、渐变文字、内嵌图片与clipPath的专门画面比较通过，图片区域差值为0。29.97fps／1080p、全片音频起点及源偏移、功能回退和编码中途取消均有真实导出回归。

独立审查发现的文字x/y坐标列表撤销回归已用实际浏览器复现并修复，恢复原文时会恢复原始坐标列表。

全套回归还发现轻量快照改变JSON字段顺序，导致撤销后的序列化比较不同；已在保持素材共享的同时保留字段顺序，并补回归。最终54项核心测试及17个浏览器／媒体检查脚本通过，相关撤销／保存流程在修复后重新验证。

尚未全面验证特殊系统字体、复杂旧SVG、所有显卡／驱动、两小时上限长片及跨平台。分段缓存、有限并行、完整差量撤销日志和代理预览分辨率留在后续阶段。

## 实测结论

本机为 Core Ultra 7 155H、RTX 4060 Laptop GPU；Edge无头渲染，1280×720、30fps、每组60帧。样例包括通用关键帧工程和内置细胞案例的高尔基体镜头。以下是一次短试验，不是完整长片或多台电脑的性能承诺。

| 路线 | 细胞镜头60帧耗时 | 说明 |
| --- | ---: | --- |
| 当前PNG截图＋libx264 | 2.246秒 | 不含载入，含编码结束等待 |
| PNG快速编码＋libx264 | 2.092秒 | 小幅改善，传输数据增多 |
| JPEG 95＋libx264 | 2.028秒 | 有损中间帧，不建议作为默认路线 |
| PNG快速编码＋NVENC | 2.515秒 | 当前短任务没有提速；硬编初始化和截图瓶颈仍存在 |
| 当前SVG状态→Canvas→WebCodecs→FFmpeg封装 | 约0.831秒 | 硬件编码已预热；0.743秒浏览器调用＋0.088秒封装，原型编码参数与基线不同 |

当前细胞镜头的截图阶段占1.816秒，约81%；SVG自身计算平均约0.955毫秒/帧。PNG改成JPEG或仅更换最终编码器，均没有消除主要等待。

新通道在该短试验中约为现有链路的2.7倍速度，但首个通用样例出现约1.7秒额外初始化等待。长片收益、不同分辨率和画质必须另测，不能把此结果直接推广为所有工程的固定倍数。

原型产物实际解码为60帧、2秒、30fps。中间帧与浏览器截图的SSIM约为0.9982，存在像素差异；正式启用前需覆盖字体、渐变、遮罩、滤镜、图片、色彩和抗锯齿。高SSIM不等于逐像素一致。

编辑端：内置工程约11.22 MB、18幕、1545个登记对象。重复4次的平均值为：整工程clone约7.25毫秒，validateProject约67.85毫秒，renderer.render约1.90毫秒。该校验会序列化并编码包含音频base64的整个工程；change还复制历史、刷新面板和时间轴，实际交互总开销会更高。

实验脚本、逐阶段原始结果和短片位于本机 `app/.work/performance-20260926/`，没有进入正式导出代码或GitHub Release。

## 推荐架构

```text
SVGFilm工程
  ├─ 不可变素材库：SVG、图片、音频
  ├─ 轻量编辑状态：剪辑、文本覆盖、组件覆盖、音轨参数
  └─ 共用时间求值与画面渲染
       ├─ 交互预览：合并鼠标事件、局部更新、可选预览分辨率
       └─ 导出任务
            ├─ 快速通道：SVG画面→Canvas视频帧→WebCodecs
            └─ 兼容通道：现有浏览器截图→FFmpeg
          →统一音频混合与MP4封装
```

### 第一阶段：快速导出通道

沿用现有renderer的同一时刻画面，只序列化当前可见来源和字幕，不复制其他隐藏镜头。浏览器内部把画面转为视频帧并编码，移除每帧CDP截图、PNG压缩、base64跨进程传输与FFmpeg重解码。音频继续使用已验证的FFmpeg混音规则。

正式实现必须采用有界帧队列、编码数据分块传输、错误／取消传播，避免把整部影片缓存在浏览器或Python内存中。编码使用精确帧时间戳和质量模式，不能通过丢帧或实时录屏换速度。初始化、渲染、编码、混音分阶段报告进度。

保留兼容通道。对于浏览器不支持的编码配置、尚未验证的SVG效果或要求原DOM截图一致性的工程，明确选择兼容导出；不可静默降帧或省略画面元素。快速模式需做像素、时长、字幕与音频对齐回归。

### 同期：让编辑状态变轻

- 素材只保存一份；撤销记录编辑差量或共享不可变素材，避免每次拖动复制音频和完整来源。
- 导入、添加素材和保存时做完整校验；普通编辑只验证受影响字段。工程大小按素材字节缓存加编辑数据计算，避免反复编码大段base64。
- 为对象、文字与镜头起点建立索引。文字内容／样式未变时不重写属性；字幕未变时复用节点，节点引用在载入时缓存。
- 拖动播放头的pointermove合并到requestAnimationFrame；一次显示刷新只求值最新时刻。修改一条字幕只更新对应画面和时间条。

内部状态调整不要求修改用户工程文件或重新制作Skill；保存时仍组装成兼容的自包含0.3工程。

### 第二阶段：重复导出与大工程

按镜头或固定帧段缓存已渲染视频。缓存键覆盖来源、文本／布局覆盖、字幕、入出点、分辨率、帧率、渲染器版本和字体环境；先缓存无音轨视频，声音最终统一混合。局部修改后只重渲染受影响片段。

缓存与分段必须使用全片整数帧网格，不能让每段各自向上取整后累计出额外帧。涉及全片时间效果或跨镜头声音时，正确处理失效范围。

资源允许时增加有限并行，先测试2个任务。按CPU、内存和显卡编码能力设上限；并行主要缩短等待，可能提高瞬时负载，不应被当作降低系统压力的首选办法。

## 不优先做的事

暂不更换React／Electron或全面重写WebGL绘图。这些改变不会直接解决截图与整工程复制开销。纯静态停留可复用帧，但现有细胞动画包含持续细微运动，不能仅凭“看起来变化小”省略帧。

## 建议验收

- 固定一组通用动画、细胞镜头和带音频工程，分别测720p／1080p及较长片段的端到端耗时和峰值内存。
- 快速导出与兼容导出有明确画面一致性范围；切点、字幕、音频和帧数保持正确。
- 导出取消能释放编码资源；回退到兼容通道有明确原因和提示。
- 编辑延迟报告中位数与P95，撤销／重做和保存回读保持原行为。
